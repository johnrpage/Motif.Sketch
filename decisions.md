# Motif Sketch: decisions so far

Motif Sketch is the first tool in the Motif suite. It combines Context Sketch and HexaSketch into one web app.

| # | Topic | Decision |
|---|---|---|
| 1 | Name | Shown to people as "Motif Sketch". The repo, solution and namespaces use `Motif.Sketch` (e.g. `Motif.Sketch.Domain`). |
| 2 | Files | One project file per system: the context diagram, plus its ports-and-adapters sketch once you start one. The sketch part is optional. |
| 3 | Import | No import of old `.contextsketch.json` / `.hexasketch.json` files. |
| 4 | Autosave | The current work autosaves to browser storage and comes back on the next visit. Saving to a file is still something you do yourself. |
| 5 | Saving | Edge and Chrome save back to the same file (File System Access API). Other browsers download a copy. |
| 6 | GitHub | Hosting on GitHub Pages only. GitHub sign-in or projects stored in a repo: maybe later, not v1. |
| 7 | Actors | Architect and Viewer (opens a shared diagram read-only). No Coding Agent in the diagram. |
| 8 | Exports | Split into Diagram Exports (SVG) and Solution Plans (Markdown). In the sketch, the plan is the `SolutionStubs` port, and the Markdown plan is its v1 adapter. |
| 9 | Arrows | An arrow points from whoever starts the interaction. Two-way is kept for the rare case where both sides start one (e.g. a webhook callback). The tool's help says this. |
| 10 | Sharing | Snapshot links: the project is compressed into the URL fragment (after `#`), so it's never sent to a server and nothing is stored. Opening the link shows a read-only view. A later edit needs a new link. |
| 11 | File extension | `.motifsketch.json`: one per tool, the same pattern as `.contextsketch.json`. |
| 12 | Browser storage | IndexedDB, not localStorage. It keeps the autosaved project and its File System Access handle, so after a refresh Save still goes to the same file (the browser asks once to allow it again). |
| 13 | Example | "Open example" loads a read-only copy of Motif Sketch's own project (context diagram and sketch), shipped with the app. It's also a test fixture. It gets built once the ports-and-adapters sketch exists. It's part of the system, so the context diagram doesn't show it. |
| 14 | One app | Architect and Viewer use one Blazor app, the "Web App" adapter on the User port. The Viewer gets a read-only mode. |
| 15 | Merged adapters | An adapter can stand for several context diagram items on any port (`sources: [...]`, not `source`). Drop an item onto an adapter to merge it in. One adapter per item still works, e.g. one app per actor. The plan says which items each adapter covers. |
| 16 | Dotted names | The plan export keeps a dotted system name as the root (`Motif.Sketch.Domain`), unlike HexaSketch, which produces `MotifSketch`. |
| 17 | Specs | The Specs adapter is drawn in the sketch. Motif Sketch adds one automatically to every driving port, just as it creates the User port. |
| 18 | Fake names | A fake is named after its port by default: "Fake Projects", which matches the generated class `FakeProjects`. |
| 19 | Real adapter names | Real adapters are named after their technology, not the context diagram item, so class names don't stutter: `BrowserFilesProjects`, `IndexedDBAutosave`, `SvgFilesDiagramExports`, `MarkdownPlanSolutionStubs`. Each adapter keeps its context diagram item as its source. |
| 20 | Acronyms | Two-letter acronyms stay in capitals in code names (`IndexedDB`, `UI`), which overrides the .NET guidelines' `Db`. |
| 21 | Checks kind | A fourth adapter kind, **Checks**, for driving ports only: a test driver that drives the application and checks what it does. It isn't a Fake, which stands in for something the application calls. The User port's Checks adapter is named "Specs" (technology xUnit) and becomes `Motif.Sketch.Specs`. Kinds are now Real, Fake, Simulated, Checks. |
| 22 | Clipboard | Copy link goes through a driven **Clipboard** port: real adapter "Browser" (Clipboard API, JS interop) → `BrowserClipboard`, plus Fake Clipboard so specs can check the copied link. The context diagram shows Clipboard as an external system. |
| 23 | Example source | The example project is compiled into the application core as an embedded resource. Reading it involves no outside I/O, so it needs no port, and specs can open it directly. |
| 24 | Context diagram changes | When the context diagram changes after the sketch exists: an adapter still carrying its source's name follows a rename, and a renamed one keeps its own name. Description and technology edits leave adapters alone. Added elements go to the unplaced list. Deleting an element removes it from its adapter's sources and flags the adapter, which stays. A type change keeps the placement. (SPEC §5.3) |
| 25 | Several tabs | One tab owns autosave. A second tab is read-only and offers "Use this tab instead", which hands ownership over (the first tab goes read-only). Viewer-mode tabs never take part. (SPEC §5.6) |
| 26 | Views on screen | Three layouts: **Context** (context diagram full width, the sketch shrunk to a live thumbnail strip on the right), **Split** (context left, sketch right, draggable divider), **Sketch** (the reverse of Context). A three-way switch in the app bar (Alt+1/2/3), a click on a thumbnail strip, or a pane's maximise button moves between them. Narrow screens get Context and Sketch only. Before a sketch exists, the sketch strip is a "Start sketch" prompt. Mockup: `docs/mockups/layout.html`. |
| 27 | Commands | A slim app bar holds the project-wide commands (title, New, Open, Save, Save as, Undo, Redo, Export, Copy link, layout switch, Help). Each pane has its own tool strip with that view's commands (add, auto-layout, fit). The project title is renamed in the app bar. The look of the bar and buttons gets its own pass: neither reference app's styling is the target. |
| 28 | Properties | A floating card in the pane that holds the selection, not a docked panel. It follows the selection: clicking open space or pressing Esc clears it and the card closes. It floats over the diagram; Fit doesn't avoid it. It opens in whichever of the pane's four corners covers least of the selected item (and of the other floating cards), preferring the farthest corner. It stays in its last corner while that corner covers nothing, so it doesn't jump on every click. |
| 29 | Unplaced list | A floating card at the sketch pane's left edge. Only its own button shrinks it, to a "N not placed" badge; clicking open space leaves it alone. The rest of HexaSketch's status line moves to a warning dot on Export. |
| 30 | Devices | Desktop and tablet can edit: pointer events for mouse, pen and touch, plus pinch-to-zoom and tap-and-hold for the context menu and rename. Phones (below about 600px) open read-only, like Viewer mode, with a note that editing needs a bigger screen. Snapshot links must work well on a phone. |
| 31 | Viewer mode | Editing controls are hidden, not disabled. The pane tool strips go, and the app bar keeps the title, a "Shared snapshot · read-only" label, the layout switch, Export and a prominent **Make a copy to edit**. Selecting an item still opens the properties card, read-only. Viewers can export SVGs and the plan. |
| 32 | Checks look | A Checks adapter is a pale slate box (`#E2E8F0` fill, solid slate outline, dark text): between solid Real and white dashed Fake. Being on a driving port is enough to tell it apart from a Fake. |
| 33 | Dark mode | The whole app, diagram canvas and thumbnails included, follows light/dark. The diagrams get a dark twin of their palette, designed in the identity pass. **Exports are always the light palette.** So the screen and an export share shapes and layout from one set of style definitions, but match colour only in light mode: SPEC §5.7 and the "exports match the screen" acceptance criterion need that wording. |
| 34 | Typeface | One open typeface, self-hosted with the app (no font CDN), for the UI and the diagrams. The core carries its width table, so labels wrap identically on every platform. Exported SVGs name it first, then fall back to the system stack; the wrapping is already fixed in the SVG. The typeface is **IBM Plex Sans** (OFL), with IBM Plex Mono available for code names. Compared against Inter, Source Sans 3, Red Hat Text, Fira Sans, Atkinson Hyperlegible Next, Geist and Public Sans; Atkinson was the runner-up for small-label legibility. |
| 35 | Chrome colour | No brand hue: the chrome reuses the diagram palette. Slate for nearly everything; orange only for single "look here" things (unsaved marker, not-placed badge, Export warning, the one primary action on screen such as Make a copy to edit), never decoration, because orange also means selection on the canvas. |
| 36 | First-run | No autosave and no link opens a blank project in the Context layout (sketch strip shows "Start sketch"). The system box is selected, with its properties card open and the name field focused. A small, dismissible welcome card in the empty space gives one line on what the tool does, the "arrows point from whoever starts the interaction" tip, and Open example / Open file. No modal. The card shows whenever editable work is empty (only the system, no sketch), so it goes when the first element is added and comes back for New. Once dismissed it never returns. Phones get the example instead (decision 50). |
| 37 | Theme choice | Follows the system by default, with a Light / Dark / System override remembered in this browser only. The override also lets a dark-mode user preview the (always light) export palette. |
| 38 | Logo | One Motif suite mark, followed by the tool's name as a wordmark ("Motif **Sketch**" in Plex). Later tools reuse the mark with their own name. The mark uses the diagram language (slate strokes, an orange accent) but isn't tied to ports and adapters. The favicon may add a small per-tool detail. The mark is **stepped squares**: three rounded squares rising diagonally, two slate outlines and the top one solid orange (a shape repeating, the literal "motif"). Chosen over two linked nodes and an M monogram. Revised in decision 54. |
| 39 | Mockups | `docs/mockups/layout.html` settled the layout. `docs/mockups/v2.html` is the look: Plex, slate-plus-orange chrome, the dark diagram twin, mark A, and the Editing, First run and Viewer states. It's a first styling pass and can still be iterated. |
| 40 | Rendering (SPEC §10.1) | The core draws each view once, as a **scene**: SVG nodes whose colours name `DiagramStyle` tokens. The SVG export writes the scene in the light palette; the screen renders the same scene with Razor, turning tokens into CSS variables (the dark twin) and adding the screen-only parts (selection, divider, the "source deleted" flag). So the screen and the export can't drift apart. |
| 41 | Interaction (SPEC §10.2) | Pointer events in C# for select, drag-to-pin, pan, pinch and drag-and-drop (touch works; HTML5 drag-and-drop doesn't). The App's one small `app.js` does only what C# can't: pointer capture, a non-passive wheel listener, hit testing (`elementsFromPoint`), a document `keydown`, `beforeunload`, theme and viewport. |
| 42 | Snapshot links (SPEC §10.3) | .NET `DeflateStream` (raw deflate) in the core, base64url, `#v1.` prefix. The core tests encode, decode and bad links without a browser. Links over **8,000 characters** are still copied, with a warning. The whole example is about 1.9 KB. If the browser refuses the clipboard, the link is shown to copy by hand. |
| 43 | Undo (SPEC §10.4) | Whole-project snapshots, capped at 200 steps, one history for both views. The §5.3 follow-up runs inside the same edit, so it's the same step. |
| 44 | Startup (SPEC §10.5) | Trimmed, no AOT, `InvariantGlobalization`, and a static splash with the mark. Measured at phase 0: about **2.8 MB** gzipped. JSON uses source generation so it survives trimming. |
| 45 | Browser tests (SPEC §10.6) | None in v1: the JS modules are thin, and `docs/manual-checks.md` is run before a release. Add Playwright if a regression gets through. |
| 46 | File handles across adapters | Adapters never reference each other, so the core passes only an opaque handle id. `globalThis.motifFileHandles` (a `Map` from id to `FileSystemFileHandle`) is the one shared browser contract: Projects adds handles to it; Autosave stores the handle itself in IndexedDB beside the work and puts it back in the map on restore. |
| 47 | Tab ownership | Web Locks (`ifAvailable`) decide which tab owns autosave. "Use this tab instead" posts on a `BroadcastChannel`; the owner writes its last autosave, goes read-only and lets the lock go. Autosave writes are coalesced: while one is in flight only the newest pending one is written next. |
| 48 | The example's system name | The plan keeps a dotted system name as its root (decision 16), so the example's system is named **`Motif.Sketch`**, which gives `Motif.Sketch.*` projects. A name with spaces ("Motif Sketch") gives `MotifSketch.*`, as before. The project title stays "Motif Sketch". |
| 49 | Plan templates | The plan exporter maps "Blazor" to `blazorwasm`, and in a Blazor solution puts driven adapters on `razorclasslib` with `Microsoft.JSInterop`, as this repo does. The golden spec checks the example's plan against `Checks/Motif.Sketch.Specs/Golden/Motif.Sketch.plan.md`. |
| 50 | Example link and phones | `#example` opens the bundled example read-only, like a snapshot link (never touching autosave) but always the current example, labelled "Example · read-only" with a banner. A phone can't edit (decision 30), so with no link and empty or no autosaved work it opens the example the same way; real autosaved work still opens as before. The README and repo Website keep the plain page link, since first-time visitors on a computer get the welcome card. |
| 51 | Toast timing | A title-only info toast ("Saved to …") goes after 3.5 s. Any toast with a sentence to read, and every warning or problem, stays 10 s, and can be closed sooner. |
| 52 | Cache busting | GitHub Pages lets browsers keep files for 10 minutes. Every JS module (the App's `app.js` and each adapter's) is fingerprinted through `Directory.Build.props` and reached through the import map, so a deploy never runs new code against old adapter scripts. `css/app.css` keeps its plain name: a standalone app's `index.html` only resolves fingerprint placeholders for scripts, so a stale stylesheet can last up to 10 minutes after a deploy. |
| 53 | The motif/ folder | Motif Sketch's own design lives in `motif/`, the Motif.NET folder for a repo's design files: `sketch.motifsketch.json` (also the bundled example, linked into the core), `plan.md`, `diagrams/` and `glossary.md`, with `motif/README.md` for people and agents and a one-line root `AGENTS.md` pointing to it. The plan and both diagrams are golden files, so the specs fail until they're re-exported after the sketch or an exporter changes. The README pictures are now Motif Sketch's own exports, and the two old `.contextsketch.json` / `.hexasketch.json` files are gone. A plain folder, not `.motif/`, because people read and edit what's in it. |
| 54 | Mark revised | The stepped squares are now an outline, a solid slate square and the orange one: a shape taking form. All three are the same size with an even 0.5 gap at both corners; before, the outlines' strokes made them larger than the solid square, so the lower pair touched and the upper pair didn't. The suite's `brand/` folder in [motif-dotnet/.github](https://github.com/motif-dotnet/.github/tree/main/brand) is now the source of the mark, the wordmarks and the favicon. The app keeps inline copies of the mark (app bar and splash) so it can use the theme's colours. |
| 55 | Shared look | The palette, fonts, app bar, menus, dialogs, toasts and shared icons come from the suite's web kit ([brand/web](https://github.com/motif-dotnet/.github/tree/main/brand/web)), copied in by `scripts/sync-suite.sh`: `css/motif.css`, `wwwroot/fonts/` and `Suite/` (namespace `Motif.Suite`). Don't edit those copies; change the kit and sync. A workflow reports drift without blocking a deploy. `css/app.css` now holds only Sketch's own styles, and `Ui` derives from the kit's `Toaster`. The mark and name are now the tool switcher, listing the Motif tools. `<code>` is code in prose, in the text colour; `.code` stays muted, for keys and formats. Like `app.css`, `motif.css` keeps a plain name (decision 52). |

## Later (not v1)

- A GitHub adapter on `SolutionStubs` that creates a repo, commits the plan, and hands it to a coding agent (e.g. by opening an issue) to inflate the stub solution. It needs GitHub sign-in, which a static Pages app can't do with standard OAuth (a token or a small backend instead). The v2 context diagram would add GitHub as an external system, and possibly the agent as a secondary actor.
- Short share links that update, hosted in a GitHub Gist (needs the same GitHub sign-in).
- In Split, drag an unplaced element straight from the context pane into the sketch.

## Still open

Questions the build raised, not yet settled:

1. **Code root vs. display name** (decision 48). The example's system is named `Motif.Sketch` so the plan's root comes out as `Motif.Sketch.*`, and that's also the name shown in the hexagon and the context diagram. Should the system get a separate, optional "code root" field instead, so it can be shown as "Motif Sketch"? That would be a small schema addition (`codeRoot` on the system element).
2. **Copy link without the clipboard.** If the browser refuses clipboard access, the link is shown in a dialog to copy by hand. Is that enough, or should Copy link always show the link too?
